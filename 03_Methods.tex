\section{Study 1: Phylo2Vec}
The overarching goal of \gls{p2v} (or Phylo2Vec)~\cite{penn2025, scheidwasser2025} is to encode phylogenetic tree topology as a vector of integers. Inspired by Yule processes~\cite{steel2001} and tree counting strategies~\cite{knuth1973, rotem1978, proskurowski1980, rohlf1983}, the core idea is to describe \emph{where} leaves are iteratively added within an existing tree topology. The construction of phylo2vec takes inspiration from the work of Rohlf~\cite{rohlf1983}, but differs in its edge‑labelling strategy and, most importantly, in preserving the tree construction process within the vector representation. Beyond this conceptual shift, our contributions are fourfold: (i) rigorous proofs of the bijectivity of the vector representation with respect to the space of binary rooted trees~\cite{penn2025}, (ii) an extended matrix format to incorporate branch length information, (iii) empirical evidence of its usability for phylogenetic inference, and (iv) robust and open-source software for manipulating phylogenetic trees using this representation~\cite{scheidwasser2025}.

The simple constraint of the phylo2vec formulation notably allows for rapid tree sampling, efficient compression, and straightforward comparison of tree topologies. In addition, the simplicity of such a vector format makes it a convenient starting object for phylogenetic tree manipulation. This is showcased in a recent software package~\cite{scheidwasser2025}, which also highlights potential avenues for phylo2vec-based phylogenetic inference, including non-traditional optimization approaches such as GradME (gradient-based balanced minimum evolution)~\cite{penn2023}.

\subsection{Definitions}
\label{p2v:definitions}
\emph{Phylo2Vec} denotes a bijective mapping from phylogenetic tree topologies to constrained integer vectors. It relies on the following assumptions on tree topology construction:

\begin{itemize}[nosep]
    \item Let $T$ be a binary, rooted, phylogenetic tree with $n \geq 2$ leaves and topology $\tau$.
    \item Each leaf is assigned a unique label $\ell \in \{0, \ldots, n-1\}$.
    \item Each internal node is assigned a unique label $\ell' \in \{n, \ldots, 2(n-1)\}$. The assignment generally depends on the node's height and descending leaves (see Section~\ref{methods:v2newick}). The root node is always labelled $2(n-1)$.
    \item Each branch (or edge) is labelled according to its target node (i.e., a branch leading to node $\nu$ is labelled $\nu$).
\end{itemize}
\input{fig/p2vtree}

Fig.~\ref{fig:p2vtree} depicts an example tree which satisfies these assumptions. Consequently, for any $n$-leaf tree topology, we define an integer vector $\boldsymbol{v}$ of length $n-1$:

\begin{equation}
    \forall n \geq 2 \quad \forall j \in \{0, \ldots, n-2\} \quad v_j \in \{0, \ldots, 2j\}
    \label{eq:p2v}
\end{equation}

We call $\mathbb{V}$ the set of vectors that satisfies Eq.~\ref{eq:p2v}. In this formulation, \textsb{$v_j$ denotes the \emph{edge} from which leaf $j + 1$ descends from} (when added to a tree with $j$ leaves). An immediate property that arises from Eq.~\ref{eq:p2v} is that the cardinality of the phylo2vec vector set equals that of the set of binary rooted trees~\cite{cavallisforza1967}. Noting $\mathbb{V}_n$ and $\mathbb{T}_n$ as, respectively, the set of vectors and binary trees with $n$ leaves:

\begin{equation}
    |\mathbb{V}_n| = \prod_{j=0}^{n-2}(2j+1) = 1\cdot3\cdot\ldots\cdot2n-3=(2n-3)!! = |\mathbb{T}_n|
    \label{eq:p2v_cardinality}
\end{equation}

Given Eq.~\ref{eq:p2v_cardinality}, showing that there exists an injection from $\mathbb{V}_n$ to $\mathbb{T}_n$ for any $n \geq 2$ is sufficient to demonstrate bijectivity between the two sets. A proof is provided in Penn \textit{et al.}~\cite{penn2025} (see~\ref{appendix:articles}).

A phylo2vec vector is said to be \textit{ordered} if it satisfies:

\begin{equation}
    \forall n \geq 2 \quad \forall j \in \{0, \ldots, n-2\} \quad v_j \in \{0, \ldots, j\}  
    \label{eq:p2v_ordered}
\end{equation}

The term \textit{ordered} refers to the fact that any leaf $i$ will, in a similar vein to Yule processes, descend from an ``older" leaf $j < i$. The cardinality of ordered trees is $\prod_{j=0}^{n-2}(j+1) = (n-1)!$. Whilst a subset of all phylo2vec vectors, ordered trees are more algorithmically efficient to manipulate (see Sections~\ref{methods:v2newick} and~\ref{methods:newick2v}) and more practical for certain downstream phylogenetic applications~\cite{penn2023, penn2025}. Importantly, the \emph{Queue Shuffle} trick~\cite{penn2023} enables the transformation of any \emph{unordered} vector $\boldsymbol{v}$ into an ordered one.

Conversely, a phylo2vec vector is said to be \textit{completely unordered} if:

\begin{equation}
    \forall n \geq 2 \quad \forall j \in \{0, \ldots, n-2\} \quad v_j \in \{j+1, \ldots, 2j\}  
    \label{eq:p2v_completelyunordered}
\end{equation}

In other words, whereas leaves from an ordered vector descend from leaf branches, leaves from a completely unordered vector attach to internal branches.

\subsection{Unpacking a vector as a tree}
\label{methods:v2newick}

Unpacking a vector satisfying the phylo2vec conditions from Eq.~\ref{eq:p2v} is performed by reading the vector from left to right, adding one leaf per vector element. Fig.~\ref{fig:v2newick} shows a detailed example of the conversion process. We start from a two-leaf tree with leaves labelled $0$ and $1$, a root labelled $2$. Following the assumptions in Section~\ref{p2v:definitions}, we label each edge according to its target node. We also add an \emph{extra root} labelled $R$, for which we draw a directed edge from $R$ to $2$. Following the definition of $v_j$ (see Section~\ref{p2v:definitions}), this additional edge is necessary to ensure that all the possible $3$ leaf placements are represented from the starting tree (and, by induction, to ensure that all possible $2n-1$ leaf placements can be represented from a $n$-leaf tree~\cite{cavallisforza1967}). From this initial state, we successively add leaves according to the values of \v, where an iteration $j$ equates to adding leaf $j+1$ from branch $v_j$. Importantly, the addition of a new leaf requires updating the labels of the internal nodes and edges. The general update rule is that the next “internal node” to be labelled is the parent of the cherry with the highest label. An illustration of this rule is presented in Fig.~\ref{fig:relabelling}.

In practice, unpacking a vector in Newick format requires two steps in the current version of the \texttt{phylo2vec} package (v1.3.1)~\cite{scheidwasser2025}. First, we build a list of “cherries” which describe a post-order traversal of the tree (Algorithm~\ref{alg:to_pairs}; see Fig.~\ref{fig:to_pairs} for an example). For ordered vectors (see Eq.~\ref{eq:p2v_ordered}), the vector translates immediately into an ordered traversal, as new leaves are added from leaf branches (i.e., extant branches). For completely unordered vectors (see Eq.~\ref{eq:p2v_completelyunordered}), insert operations are needed to preserve the post-order nature of the cherry list, with the insert position depending on $v_j$ and $j$. From this list of cherries, we can form a Newick representation of the tree by iteratively merging Newick substrings initiated from the cherry list (see Fig.~\ref{fig:build_newick} for an example).

\subsection{Packing a Newick tree into a vector}
\label{methods:newick2v}

Converting a Newick representation of a binary, rooted tree into a phylo2vec vector requires three steps. First, the Newick string is parsed from left to right, where substrings of the form $(c_1, c_2)p$ are successively converted into a list of triplets that we call \emph{ancestry}. Importantly, the Newick string need not to have explicit parental nodes for this conversion process to function, as similar algorithms can be derived without them~\cite{scheidwasser2025}. Fig.~\ref{fig:parse-snake} shows an example of this process for the Newick string obtained in Fig.~\ref{fig:build_newick}. 

\input{fig/parse}

As the obtained \emph{ancestry} is not sorted in the same post-order manner as the cherry list in Section~\ref{methods:v2newick}, a sorting step is necessary. In the present of parental labels, we assume that the parental node labels follow a similar labelling order than in the re-labelling step illustrated by Fig.~\ref{fig:relabelling} and simply sort the ancestry matrix in ascending order by the parental column. In the absence of explicit parental labels, we utilise the fact that the input is \emph{locally ordered}. In other words, two cherries with the same minimum label 

\begin{equation*}
    \begin{pmatrix}
        a & b \\
        a & c \\
    \end{pmatrix}
\end{equation*}

must be ordered post-orderly, as we first process the input Newick from left to right as deep as possible (Fig.~\ref{fig:parse-snake}). In Newick format, they would be written as \texttt{((a, b)c)}. From this observation, we derive a sorting index by processing the ancestry from top to bottom described in Algorithm~\ref{alg:order_cherries}. An illustration, using the output from Fig.~\ref{fig:parse-snake} as an example, is presented in Fig.~\ref{fig:ordercherries}

\input{alg/order_cherries_no_parents}

\input{fig/order_cherries_no_parents}

The obtained ordered ancestry mirrors the cherry list in Algorithm~\ref{alg:to_pairs}. To infer the inverse operation and finally recover a phylo2vec vector \v, we observe that each cherry (the first two columns of the ancestry) comprises a newly added leaf (right) and its smallest descendant (left). To infer the branch from which the added leaf descends, we need to count how many cherries have already been placed at labels strictly smaller than its own. To that end, we employ Fenwick trees~\cite{ryabko1992, fenwick1994}, which support dynamic prefix-sum queries for tracking the number of earlier placements. A sketch of the implemented algorithm in Scheidwasser \textit{et al.}~\cite{scheidwasser2025} is presented in Algorithm~\ref{alg:buildvector}, with an illustrated example in Fig.~\ref{fig:build_vector}.

\subsubsection{Cherry list}

The naive implementation presented in Algorithm~\ref{alg:to_pairs} has a best-case complexity of $\bigO(n)$ for ordered vectors (only \texttt{append} operations, which are $\bigO(1)$), and worst-case complexity of $\bigO(n^2)$ for completely unordered vectors (only \texttt{insert} operations, which are $\bigO(n)$). As $n$ grows, the ratio of leaf placements which satisfy $v_j < j$ tends to $1/2$, thus making the average complexity $\bigO(n^{1.5})$ or $\bigO(n\sqrt{n})$. An optimized implementation~\cite{scheidwasser2025} makes use of \gls{avl} trees~\cite{adelson1962}, a self-balancing binary search tree where insert operations are $\bigO(\log n)$ no matter the insertion position. Thus, the best, average, and worst-case complexity of an \gls{avl}-based algorithm is $\bigO(n \log n)$. With that in mind, the current version of the \texttt{phylo2vec} package~\cite{scheidwasser2025} employs the naive algorithm for ordered vectors $\big(\bigO(n)\big)$, and the \gls{avl}-based algorithm for non-ordered vectors $\big(\bigO(n\log n)\big)$ as $\log n$ grows less quickly than $\sqrt n$.

\subsubsection{Newick building}

In Fig.~\ref{fig:build_newick}, the complexity of cache building is $\bigO(n \log n)$, as the number of decimal digits in an integer $N$ is $\lfloor\log N\rfloor+1$ \textcolor{red}{source}. The second stage involves $n-1$ iterations (one per pair), making the time complexity linear in the number of steps. However, the actual time complexity will largely depend on string concatenation operations, which themselves are impacted by tree topology. We can distinguish a few scenarios to provide a rough estimate of best-, average- and worst-case complexity. On the one hand, imbalanced trees such as caterpillar trees (e.g., \v~$= \begin{pmatrix} 0 & 0 & 0 & ... & 0\end{pmatrix}$) will involve consecutive string concatenations with an ever growing string at $\kappa_0$, thus producing a worst-case complexity of $O(n^2)$. Conversely, balanced trees (e.g., \v~$= \begin{pmatrix} 0 & 1 & 0 & 1 & ... & 0 & 1\end{pmatrix}$) implies a more even distribution of the concatenation operations: each character will be copied at most $O(\log n)$ times as it propagates up the tree levels, yielding a best-case complexity of $O(n \log n)$. A reasonable estimate for the the average complexity is $\bigO(n \sqrt n)$, as the average height of binary trees is $\bigO(\sqrt n)$~\cite{flajolet1982}.

\subsubsection{Newick parsing}

Since each character is examined at most once, the complexity of the parsing function is bounded by the length of the Newick string, resulting in a time complexity of $O(L)$, where $L$ is the number of characters in the Newick string. Since Newick format representations grow linearly with the number of leaves, the time complexity can be written as $O(n)$.

\subsubsection{Ancestry sorting}

Both algorithms for ancestry sorting run in linear $\big(\bigO(n)\big)$ time. If the input Newick contained explicit parent labels, we can utilise the ancestry's parent column as a sorting index to reorder the ancestry rows. This is possible because the parent column contain unique internal labels $n, ..., 2(n-1)$. Conversely, Algorithm~\ref{alg:order_cherries} exploits local orderings to derive a sorting index, which is also performed in linear time. However, it requires a stable sorting step which is linearithmic $\big(\bigO(n\log n)\big)$.

\subsubsection{Vector building}

As mentioned in Section~\ref{methods:newick2v}, building a vector from a sorted ancestry requires the implementation of Fenwick trees for tracking cherry placements. Both prefix sum and updates are logarithmic operations, making the algorithm linearithmic in time $\big(\bigO(n\log n)\big)$.

\subsection{Phylo2Mat: extending phylo2vec vectors with branch length annotations}

Whereas the topology of a tree depicts the evolutionary relationships between different entities, branch lengths are essential to quantify the amount of evolution that has occurred along each lineage. To incorporate that information, we extend the vector formulation of phylo2vec into a matrix (we call the resulting format \emph{phylo2mat} with two columns for branch length annotations. The order of the branch lengths when representing the topology \v~as an ancestry, i.e., a list of cherries represented as triplets $(c_1, c_2, p)$, where $c_1$ and $c_2$ are children nodes and $p$ the parental node (see Section~\ref{methods:newick2v}). Fig.~\ref{fig:phylo2mat} shows an example on how to annotate a tree from a phylo2mat matrix. 

All conversion algorithms described in Section~\ref{methods:v2newick} and Section~\ref{methods:newick2v} are broadly applicable to this extended format. During cherry ordering (Algorithm~\ref{alg:order_cherries}), an extra step is required to make the matrix formulation invariant to cherry permutations. \newline For instance, the isomorphic Newick strings \texttt{((1:0.1,2:0.2)3:0.3);} and \texttt{((2:0.2,1:0.1)3:0.3)} should yield the same matrix. To that end, we enforce an extra row ordering step, whereby each triplet is sorted as $c_1', c_2', p$ such that the smallest descendant of $c_1'$ is smaller than that of $c_2'$. This operation, in addition to branch length parsing in Newick strings, incur some additional overhead without however changing algorithm complexity.

\subsection{Implementation}

The original version of phylo2vec was purely implemented in Python, using \texttt{NumPy}~\cite{harris2020} for vector operations and \texttt{numba}~\cite{lam2015} to optimize NumPy-based functions using just-in-time compilation. The current implementation (v1.3.1)~\cite{scheidwasser2025} features several optimisations from an algorithmic (\gls{avl} tree-based conversion from \v~to Newick, Fenwick tree-based conversion from Newick to \v) and computational efficiency point of view, with core functions written in Rust~\cite{rust}. More specifically, More specifically, we chose Rust for its high performance, memory safety and interoperability with other high-level programming languages, notably via \texttt{PyO3} (\url{https://pyo3.rs/v0.25.1/}) for Python and \texttt{rextendr}~\cite{wilke2025} for R. In addition, we provide comprehensive documentation with notebook-based demos using \texttt{Read the Docs} (\url{https://about.readthedocs.com/}), and a robust pipeline for continous integration (CI) and continuous delivery (CD) using GitHub Actions (\url{https://docs.github.com/en/actions/get-started/understand-github-actions}) to ensure reliable deployments while maintaining high code quality.

\subsection{Properties}
We have been interested in studying four properties of Phylo2Vec/Phylo2Mat objects: compressibility, fast sampling, fast comparison, and their metricness.

For sampling and comparison, we perform benchmarking experiments for $n$ = 10,000 to $n$ = 100,000 leaves. We benchmark both the Rust and Python endpoints, using $x$ random unordered trees per round. For all benchmarks, we compare against ape in R, and dendropy, and ete3 in Python.

For distance measure, we employ a simple Hamming distance measure between vectors, and we compare it to traditional distance measures between trees: number of \gls{spr}, \gls{rf}, and \gls{kf}.
